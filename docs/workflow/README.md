# 露早歌曲制作工作流

这是唯一需要维护的制作说明。它只规定目录、命名和技术验收，不规定一首歌必须使用
哪些模型、插件或混音参数。每首歌从最简单的可听版本开始，实际问题由试听决定。

## 工作区

```text
露早/
├── 00. Recent Listening/       最近需要反复听的少量副本
├── 10. In Progress/            正在制作
├── 20. On Hold/                暂停但以后可能继续
├── 30. Completed/              已确认完成
├── 90. Shared Resources/       确实跨歌曲复用的素材
└── 99. Tools and Guide/        本地工具入口，可保持为空
```

歌曲名使用三位排序号与真实歌名、翻唱署名：

```text
013. 很抱歉我这么可爱-小雾uya/
├── 00. Listen/                 当前需要比较的少量文件
├── 10. Sources/                原始音频、视频、歌词和参考
├── 20. AI/                     分离、去和声、去混响与 RIFT Run
├── 30. Mix/                    当前工程、脚本、stem 与渲染
├── 40. Versions/               已冻结且不再覆盖的版本
└── 90. Deliverables/           最终母带和视频
```

文件都是普通物理文件。硬盘和 NAS 空间优先换取直观与安全，不使用哈希对象库、内部
slug 或符号链接作为人的入口。具体命令以 `mixctl --help` 为准。

## 文件与 Run 命名

文件名统一以 `歌名-歌手` 开头，处理链从左到右追加，不使用 `from`：

```text
很抱歉我这么可爱-小雾uya-bs124-vocal-l1.wav
很抱歉我这么可爱-小雾uya-bs124-vocal-l1-anvuew-karaoke-lead.wav
很抱歉我这么可爱-小雾uya-bs124-vocal-l1-anvuew-karaoke-lead-rift25k.wav
```

一个 AI Run 代表一个模型和一组共同参数。参数写进 Run 名，不为每个输入、输出或
机器再建子目录：

```text
20. AI/
├── 01. MVSEP-BS124/
├── 02. Anvuew-Karaoke/
└── 03. RIFT25K-k0-s32-ds0p2-spk0p8-cfg0p7-rf0-seed7/
```

MVSEP BS-Roformer 124 的六轨全部保留：

```text
bs124-vocal
bs124-vocal-l1              默认优先进入后续处理
bs124-vocal-l2
bs124-vocal-l3
bs124-instrumental
bs124-instrumental-l1
```

去和声、去混响和其他公开模型都是可选分支，只在实际使用时追加模型名。RIFT 同参数
候选应使用 `kaggle_rift.py` 批量提交，让 Kaggle 两块 T4 动态领取任务。

## 一首歌如何推进

默认顺序不是强制处理链，而是一组判断关口：

1. 保存来源，确认主唱、伴奏、参考和视频的身份、时长与采样率。
2. 保存 MVSEP 六轨，独奏判断；通常先用 `vocal-l1`。
3. 先跑最简单的 RIFT 基准；仅在听到明确问题时尝试去和声、去混响或参数矩阵。
4. 与目标伴奏检查固定偏移、局部节拍、速度漂移和总采样点数。
5. 只修明确有问题的窗口，保留上下文并使用自然交叉淡化。
6. 按电平、遮蔽、动态、自动化、空间的顺序混音；和声、重放和湿声保持独立 stem。
7. 先冻结 premaster，再按歌曲需要生成 listening master 和视频。

每次版本用简短英文说明听感变化，例如：

```text
01. Initial Balance
02. Fix 00m17s
03. Fix 01m56s
04. Relax Bus Dynamics
05. Wider and Louder Harmony
```

同一版本不覆盖。改变了可听结果就建立新版本；无须另写版本流水账，版本名、脚本和
同目录输出就是记录。`mixctl version` 会先在隐藏临时目录完成副本，再原子发布。

正式渲染前用 `mixctl preflight` 检查全部输入；缺失或无法解析时必须停止。

### 对齐锚点

不要根据总时长猜漂移。同一次演唱的 RIFT 与源人声比较人声轨；不同翻唱接入伴奏时
比较两边的伴奏轨，不拿不同歌手的人声硬做相关。`align_audio.py detect` 只写报告和
建议锚点，不渲染音频。

检测使用慢速 log-RMS 包络：先在默认正负 8 秒内找全局偏移，再以 40 秒窗口、正负
0.3 秒范围测局部残差，并按相关度加权拟合线性时钟漂移；明显离群的局部窗口不会进入
最终拟合。搜索参数和每个窗口的相关系数都写进报告。至少三个窗口支持拟合且最大残差
不超过默认 15 ms 时，报告才会标记 `safe_to_apply=true`，建议文件才包含拟合后的首尾
两个有效锚点；否则建议文件只有注释，不能直接交给 `apply`。搜索范围、窗口、阈值和
最大拟合残差均可在 `detect --help` 中显式调整。

试听或查看报告后，可以人工修正或增加乐句边界锚点。文件每行依次是输入时间和目标
伴奏时间：

```text
# SOURCE_TIME TARGET_TIME
00:00.000 00:00.000
01:12.400 01:12.418
02:35.700 02:35.731
```

先用 `align_audio.py check` 只读检查固定偏移、累计漂移和分段变速，再用 `apply` 渲染。
交叉淡化和最大变速必须显式指定；超过上限会停止。

脚本按区间使用 FFmpeg `atempo` 保持音高，并在锚点附近交叉淡化；每段使用额外真实
音频作为处理保护区，不在 `atempo` 后补零凑长度。输出采样率、声道数继承输入，总
采样点数严格匹配参考。不同演唱版本只在乐句边界放锚点，不逐字量化。
只有固定偏移时也写两个以上锚点，让报告明确显示各点偏移一致。

### 乐句音量自动化

先用 `analyze_reference_energy.py` 对原曲做只读慢速能量分析。报告用于判断段落趋势，
不生成音频或增益文件。

判断编曲段落能量时输入原曲完整混音；只研究原唱自身强弱时输入分离后的原唱人声。
报告是参考证据，不应逐点复制成自动化。结合原曲和实际混音试听，再把确实太强、太弱
或被伴奏遮住的范围写进
`vocal-gain.txt`。每行依次是开始、结束和 dB；重叠范围会按 dB 相加，因此可在段落
调整上叠加少数局部修正：

```text
# START END GAIN_DB
00:18.200 00:24.800 +1.0
00:47.500 00:51.000 -1.5
01:16.000 01:29.000 +0.8
```

`apply_gain_automation.py` 的交叉过渡时间必须显式填写。工具不分析情绪或自动拉平
乐句，只执行人工决定；区间外样本不变，输出 Float WAV 且拒绝覆盖。轻压缩放在这步
之后，整轨重压缩不是默认步骤。

## 混音与空间的技术边界

- 中间 stem 使用 Float WAV；正式量化只在最终母带发生一次。
- 主唱对齐、EQ、压缩、和声比例和响度都是歌曲专属决定，不复制旧歌参数。
- M7 日常从 `Small Vox Room` 开始，需要更贴近时比较 `Studio B Close`；它们只是
  起点，歌曲需要时仍从完整库选择其他空间。
- M7 默认完整且原样读取 IR，不裁切、不淡出；预延迟和 wet 电平必须由歌曲显式给出。
- M7 返回默认与输入保持完全相同的采样点数，避免卷积尾巴意外延长工程；确实需要
  完整尾响时显式使用 `--keep-tail`。发生有效尾响截断时脚本会报警。
- `render_m7_returns.py` 在使用和声时要求 main/harmony send 等长，并拒绝覆盖已有输出。
- `apply_breath_control.py` 只接受单声道 lead vocal，区域越过文件结尾会报错。
- 限制器应启用延迟补偿。Float 转 PCM24 时在最终量化点使用一次 TPDF dither，后续
  不再重复抖动。

仓库不保存私有 IR。`render_m7_returns.py` 默认使用 `small-vox-room`，第二个日常起点是
`studio-b-close`；其他 IR 显式传入同名 L/R 对。比较时保持 wet RMS 一致，把胜出名称
写进版本名。缩短 IR 必须同时显式设置裁切比例与尾部淡出；Float wet stem 不做峰值
归一化。等长返回需要 send 尾部有足够静音，否则延长 send 或使用 `--keep-tail`。

局部呼吸控制也没有听感默认值。`apply_breath_control.py` 的区域、频段、阈值、比例和
时间参数必须针对当前人声试听，不能复制成歌曲标准。

## 母带、视频与验收

保留两类用途，不用一个文件兼任：

- `premaster`：动态较宽松，通常约 -14 LUFS，适合归档和继续处理；
- `listening-master`：响度由歌曲和用途决定，但必须记录实测 LUFS、LRA 与 dBTP。

音频通常交付 44.1 kHz / 24-bit WAV 与 FLAC。平台要求 96 kHz ALAC 时只把它视为封装
规格，升采样不会产生新信息；复制视频流时不要默认使用 `-shortest`，避免截掉末尾音频
帧。

最终文件用 `mixctl delivery` 完整解码并测量，而不只读取头部。视频还要用母带作为
`--reference` 检查时长，试听首尾、单声道折叠和局部修复边界，并确认视频流未重编码、
没有残留原音轨。失败时修正并生成新输出，不覆盖旧文件。

## 完成条件

- 听感上已确认主唱、伴奏、和声、动态和空间关系；
- 当前版本包含实际输入、渲染脚本和输出，不依赖旧歌曲目录；
- 母带与视频完整解码，格式、时长、LUFS、LRA、dBTP 和首尾均通过；
- 当前试听副本已更新，项目整体移动到 `30. Completed`；
- 除非出现新的听感目标，不再继续为了流程本身增加文件或文档。
